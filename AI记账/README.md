# AI 校园记账管家 · 月末防吃土

> 一句话记账 + 周期预算引擎 + 校园平替 + 冲动消费冷静期
> 纯前端、零依赖、零构建，**双击 `AI记账.html` 就能跑**（断网可演示）。

> **出包三步，顺序不能反**：`python rebundle.py`（真打包，打印「（无变化）」= 已同步）→ `python _qa_smoke.py`（7 条冒烟：模块挂载 / 备注清洗 / 记账落库）→ `python _qa_bundle.py --static-only`（11 条只读：清单↔磁盘 / 块数 / 逐块逐字节 / 索引表）。出手前想只核验不写盘，用 `python rebundle.py --check`。**注意**：`rebundle.py` 的 `--check` 是后补的只读分支 —— 在它出现之前，`python rebundle.py --check` 会丢掉参数、执行一次真实打包并写盘，`exit 0` 只代表「打包成功」。这类「会写盘的命令被当成只读命令」正是 gu.js 被挤出打包清单那次事故的成因形态。

> **为什么不用框架**：评审现场可能没有网络。本项目不使用 npm、不使用打包器、不引用任何 CDN，
> 所有图表（环形进度、甜甜圈、柱状图）都是手写 SVG。

> **为什么不用 ES Module**：`file://` 协议下浏览器会以 CORS 为由拦截 `import`。
> 因此全部采用传统 `<script src>` 顺序加载 + 全局命名空间 `window.AJ`，
> 同时每个逻辑文件末尾保留 UMD 兼容尾，可在 Node 里直接 `require` 做单测。

## 三、功能说明

> 注：本文档用 `🛒` `💡` `💰` 等 emoji 作**语义标签**方便阅读；实际界面已统一为内联 SVG 线性图标（`#i-radar` / `#i-bulb` / `#i-wallet`），页面上不再显示 emoji。

### 1. 对话式自然语言记账

微信风格聊天窗，AI 气泡在左、用户在右，回车发送。

**一句话多笔自动拆分**：

```
今天中午吃黄焖鸡花了18，晚上和舍友AA聚餐付了50
  → 餐饮 / 午饭 / ¥18.00 / 备注「黄焖鸡」/ 2025-06-18
  → 社交 / 聚餐 / ¥50.00 / 备注「和舍友AA聚餐」/ 2025-06-18
```

解析规则（`nlp.js`）：

| 能力 | 说明 |
| --- | --- |
| 分句 | 按 `，。；、,!?！？~` 与「还有/然后/另外/加上/以及/顺便」切分；无金额的分句合并到相邻分句 |
| 金额 | `18` `18.5` `¥18` `18元` `18块` `花了18` `付了50`；中文数字 `十八` `五十` `两百` `一百二`(120) `三十五` |
| 多金额配对 | 「打车 15 和奶茶 12」按出现顺序切段，一段一笔 |
| 时间 | 今天/昨天/前天/今早/昨晚… → `YYYY-MM-DD`；无时间词时**继承上一笔的日期** |
| 餐段 | 早上/中午/下午/晚上/夜宵；无关键词时按当前钟点推断（<10 早餐，11-14 午餐，17-21 晚餐） |
| 分类 | 9 类关键词打分：`最长命中词长度 × 10 + 命中词数`，平手按分类表顺序 |
| 动机 | 命中情绪词 → `情绪`，否则 `刚需`；服装鞋包/数码/美妆 → `want: true` |
| 收入 | 生活费/到账/兼职/工资/奖学金/助学金/家里打/退款/收到红包 → `type: 'income'`，不计入支出 |
| 备注 | 剔除金额、时间词、动词量词后的剩余文本；为空时用分类名兜底 |

中文数字误判防护：数字后跟量词（`一双鞋`）或前无动词且不在句末（`三食堂`）时不算金额。

解析失败（无金额）时不再整句否定：先判意图，再只问缺的那个槽位——`奶茶` → 「奶茶多少钱？点一下就行 👇」
+ 3 个金额按钮 + 「自己填」；同一件事追问到第四次才给人工出口。完整阶梯见第八节。

### 2. 「月末防吃土」周期预算引擎

**按发钱日算周期，不是自然月**。发钱日设为 15 号时，周期就是 15 号到次月 14 号。

- `getCycle(today, payday, cycleLen)` → `{start, end, totalDays, passedDays, remainingDays}`
- `getBudgetState({total, spent, remainingDays, todaySpent})` → `{remaining, dailyAllowance, isOver, overBy, todayRemain, status}`
- `simulatePurchase({amount, state, remainingDays})` → `{newDaily, noodleDays, verdict, message}`

状态分级：日均 < ¥20 → `danger`；< ¥40 → `tight`；否则 `safe`。

购买模拟示例（剩 ¥450 / 9 天，买 ¥400）：

> 买完这笔，接下来 9 天日均只剩 ¥5.6。真买的话大概要 6 天泡面配食堂免费汤🥲

（`noodleDays = ceil((15 - newDaily) / 15 × remainingDays)`）

设置面板（完整版齿轮 / 简洁版「我的」→「设置」，两者共用同一面板）可改「每月生活费 / 每月发钱日 / 单笔冷静期阈值」，改完立即重算。

### 4. 冲动消费「冷静期」拦截

触发条件：`type === 'expense'` 且（`motivation === '情绪'` 或 `want === true`）且 `amount >= 冷静期阈值`（默认 ¥50）。

>
> **[坚持购买]** **[算了，不买了]**

### 8. 进账（收入）与周期重置

**三种录入入口**：`记收入` 胶囊 → 表单（金额 / 来源 / 日期 / 备注）；聊天里说「收到生活费2000」「兼职赚了300」；截图识别。

- 收入写入 `{ type: 'income', category: '收入', source: '生活费' }`，**不计入支出统计**，但参与「收支概览」与储蓄率计算。
- 来源枚举：生活费 / 兼职 / 奖学金 / 助学金 / 红包 / 退款 / 其他；聊天识别时由 `nlp.detectIncomeSource()` 按关键词推断（「到账」单独出现时按生活费理解）。
- 看板新增「收支概览」卡：本周期 **收入 / 支出 / 结余 / 储蓄率** 四格。
  `储蓄率 = (收入 - 支出) / 收入 × 100%`，收入为 0 时显示 `—`（不会出现 NaN / Infinity）；结余为负时红色显示。
- **生活费到账追问**（大白话）：当收入 ≥ ¥300 且（来源是生活费 或 备注含 生活费/到账/打钱/给我转）时，入账后追问
  > 这笔 ¥2,000 是新的生活费到账吗？要不要从现在起重新算一个周期？（就是把预算也换成这笔钱，日均重新算一遍）

  - **[要，从现在重新算]** → `budget.cycleStart = 该笔日期`、`budget.total = 该笔金额`，立即重算并回「好，新一轮开始：¥2,000 从 10-23 用到 11-22，还有 30 天，日均 ¥66.67。」
  - **[不用，只记这一笔]** → 只留流水，提示「行，这笔只当流水记着，预算没动。」
  - 同一笔只问一次（账单上记 `askedCycle: true`），换一笔新收入会重新问。
- **周期自定义起点**：`getCycle(today, payday, cycleLen, overrideStart)` 第四参传 `'YYYY-MM-DD'`（第三参直接传日期字符串也支持）。
  起点 ≤ 今天时生效：`start = overrideStart`，`end = 起点之后的第一个发钱日 - 1 天`；起点晚于今天则回退发钱日算法。
  不传时**行为与 v1 完全一致**（发钱日推算）。设置面板「预算设置」里显示「本周期：10-23 ~ 11-22（自定义起点）」并给一个「恢复按发钱日算」按钮清掉 `cycleStart`。
- CSV 的 `bills.csv` 在末尾追加 `收支` 列（前 6 列顺序不变）。

### 9. 账单分析（导入支付宝 / 微信 / 银行 CSV 或 Excel）

`analysis.js`（`window.AJ.analysis`）继续负责全部账单字段识别；`xlsx.js`（`window.AJ.xlsx`）只把 Excel 首个工作表转成 CSV 文本，避免出现第二套字段规则。顶部 `📊 账单分析` → 全屏 sheet（不是窄弹窗）。

**导入格式与解码**

| 环节 | 处理 |
| --- | --- |
| 解码 | 先 `new TextDecoder('utf-8', {fatal:true})`；抛错再试 `gbk` → `gb18030` → `big5`。每次解码后都统计 `U+FFFD` 与不可见控制字符占比，**> 30% 判「无法识别文件编码」**（否则 `TextDecoder('gbk')` 对任意二进制都不抛错，PDF / xlsx 会被硬解成一大段乱码） |
| 表头定位 | 扫描**前 30 行**，取同时含「时间类列」与「金额类列」的那一行（支付宝 / 微信导出文件顶部有多行说明） |
| 列名匹配 | 大小写 / 空格 / 括号 / 全半角归一后包含匹配：时间（交易时间 / 交易创建时间 / 记账日期 / 交易日期 / 时间 / 日期）、金额（金额 / 交易金额 / 发生额 / 本次金额 / 订单金额 / 金额(元)）、**借方列**（借方发生额 / 支出金额 / 借方金额）、**贷方列**（贷方发生额 / 收入金额 / 贷方金额）、收支（收/支 / 收支 / 交易类型 / 借贷标志 / 方向）、对方（交易对方 / 对方户名 / 商户名称 / 对方）、说明（商品说明 / 商品名称 / 商品 / 摘要 / 交易说明 / 备注 / 用途）、分类（交易分类 / 分类） |
| 说明列回退 | 一列文件里「备注」常整列为空，因此说明类列会全部收集成候选并按权重降序排列：「商品」系列权重 **96~100** 高于「备注」80，取值时**取第一个非空的那个**，避免丢掉微信账单的商品名 |
| 金额清洗 | 去掉 `¥ ￥ , " 空格`，处理 `-` 与 `( )` 负数写法 |
| 收支判定 | 收入 / 收 / 贷 → income；支出 / 支 / 借 → expense；**`不计收支` / `不计入收支` → excluded**（微信转账行的标准写法）；无该列时金额为负判 expense；单列「借方发生额 / 贷方发生额」按**命中的表头文本**判断而不是按别名常量 |
| 借贷双列 | 银行流水同时有「借方发生额」「贷方发生额」时走双列分支：借方有值 → expense、贷方有值 → income、两列都有值取绝对值较大者并标 `amountConflict`；贷方行不会再因为主金额列为空被整行跳过 |
| 转账兜底 | 见下方「转账型收入」判定表；提现 / 还款 / 借贷类无论方向一律 `excluded: true` |
| CSV 解析 | 逐字符状态机，支持字段内逗号与 `""` 转义（不用 `split(',')`）、自动识别逗号 / 制表符 / 分号 |

**「转账」类记录怎么算**（`isWithdrawOrRepay` / `isTransferText`，优先级自上而下）

| 情形 | 判定 | 例子 |
| --- | --- | --- |
| `收/支 = 不计收支 / 不计入收支` | 永远 `excluded` | 微信转账行 |
| 分类 / 交易类型含 `提现 / 还款 / 信用卡还 / 还花呗 / 投资理财 / 理财赎回 / 借贷` | 永远 `excluded`（收入方向也不算收入） | 「零钱提现」「信用卡还款」 |
| `收/支 = 收入` | **计入收入**，即使 `交易类型 = 转账`；同时标 `transferIncome: true` | 爸妈用微信转账打生活费 |
| 支出方向 + 文字含 `转账 / 转入 / 转出 / 汇款` | `excluded`（给室友转账不是消费） | 「转账给李四」 |

提现 / 还款只匹配「分类 + 交易类型」这类标签列，**不匹配对方名 / 商品名**，所以「借贷宝超市」不会因为商户名叫「借贷宝」被误杀。
转账型收入会在导入状态栏提示「其中 N 条为转账型收入，已计入；若为本人账户互转请手动排除」（`parseInfo.transferIncomeCount`），把「要不要算」交回给用户。

**分类映射**（`data.js` 的 `BILL_CATEGORY_MAP`）：`餐饮→餐饮`、`交通→交通`、`购物→购物`、`日用→购物`、`居住→居住`、`通讯→居住`、`医疗→医疗`、`教育→学习`、`娱乐→娱乐`、`人情往来→社交`、`收入→收入`、`其他→其他`；
`转账`、`还款` 默认标记 `excluded: true`（按上表优先级，**收入方向的转账例外**）。映射未命中时回退 `nlp.classify(对方 + 说明)`，仍无 → `其他`。

**去重**：同 `日期 + 金额 + 对方` 判疑似重复（跨文件与文件内都判），**默认只标记不删除**；报告第 8 节单列，勾选「排除疑似重复项重新统计」后重新出报告。

**9 节报告**（`report(rows, {month, excludeDuplicates, files})`）

1. 总览：总支出 / 总收入 / 结余 / 笔数 + 与上月对比（上月无数据标 `—`）、笔均、日均（按有记录的天数）
2. 分类占比与环比：金额、占比、笔数、笔均、与上月同类增减
3. Top 10 单笔大额
4. Top 10 高频商户（按笔数）
5. 周末 vs 工作日：笔数、合计、**日均**（金额 ÷ 该桶内有记录的天数，不是总额直接比）
6. 订阅型支出：连续 ≥3 个月「同对方 + 同金额」，标本月是否仍在扣 + 折合一年
7. 异常大额：单笔 > 该分类其余各笔笔均 ×3（该分类不足 3 笔不判）
8. 疑似重复：配对清单
9. 解析情况：每个文件的编码、表头行号、有效记录数、**前置说明行数**（表头之前的导出说明）、**无效数据行数**（表头之后解析不出的行）、列映射（借贷双列时**借方 / 贷方两列都列出**）

**消费建议**（`insights(report, budgetState)`，3~5 条，每条都带真实算出来的数字）覆盖：恩格尔 > 50%、情绪型占比 > 15%、21:00 后餐饮占比 ≥ 25%、小额（< ¥20）笔数占比 > 30%、订阅年化金额、周末 / 工作日日均 > 2 倍、某分类环比 > 30%、储蓄率 < 10%。语气克制，不下价值判断，不推荐具体产品 / 平台 / 理财。

**交互**：上传区（点击 / 拖拽 / 多选 `.csv` / `.txt` / `.xlsx`）→ Excel 工作簿先在本机解压并转为 CSV → 摘要 → 9 节可折叠报告（默认展开总览与分类）→ 底部 `导出 Markdown` / `把导入记录并入账本`（二次确认，明示会改变预算统计）/ `清空导入`。
**默认只分析不写账本**。分类占比用手写横向条形图，不引第三方图表库。

### 10. 截屏识别记账（三层降级）

`ocr.js`（`window.AJ.ocr`）。顶部 `📷 截屏记账` → 弹窗：选图 / 拖拽 / **Ctrl+V 粘贴** → 预览 → 开始识别 → 待确认卡。

```
1) 浏览器原生 window.TextDetector    → 本地识别，零网络
2) 云 OCR（可选，腾讯云 GeneralBasicOCR）→ 用户在设置里填 SecretId / SecretKey / Region 后才可能启用
3) 演示模式：内置 3 份示例小票         → 仅由用户显式点选（点「示例小票」），auto 模式绝不自动回落到示例
```

- **演示样例永远不会冒充识别结果**：`detect({mode:'auto'})` 在前两层都不可用时返回
  `{ok:false, source:'none', text:'', reason, tried:['native','cloud']}`，`text` 恒为空串；
  只有用户主动点「示例小票」（`mode:'demo'`）才会返回内置样例。打开弹窗时状态行就直接说明
  当前环境属于「可以离线识别 / 将用云端识别（需联网） / 当前只能用示例小票或手动录入」哪一种。
- 识别失败时的卡片给三个可操作出口：**用示例小票演示**、**配置云 OCR**（打开统一设置面板并定位到 OCR 区；
  已配置凭据时按钮文案变成「检查云 OCR 设置」）、**手动录入**（关闭弹窗、聚焦对话输入框）。
  失败文案按**实际失败的层**归因，不会一律甩锅给设备：设备没有识别能力 → 「不是你操作的问题，是这台设备缺少本地识别能力」；
  已配云 OCR 但云端请求失败 → 「云端识别没成功 —— 凭据已配置，但这次请求失败」（并提示查网络/跨域、核对凭据）；
  本地识别读出空文本 → 「可能是这张图太模糊」。
- 双保险：若结果 `source === 'demo'` 且当前存在用户上传的图片，预览图会被隐藏，结果卡顶部加黄色提示
  「⚠️ 这是内置示例，不是你上传的截图，仅用于演示流程」。
- 云 OCR 用 **Web Crypto** 实现 TC3-HMAC-SHA256 签名（`crypto.subtle.importKey / digest / sign`），不引第三方库；
  凭据单独存 `localStorage['ai_jizhang_ocr']`，设置面板明示「Key 存在本机浏览器，仅本地调用，勿在公用电脑填写」，并提供「清除凭据」。
- **未配置凭据时不会发起任何网络请求**（`ocr.js` 是全项目唯一出现 `fetch` 的文件，且只在用户主动点识别且凭据存在时执行）。
- 失败一律返回结构化结果并给出下一步（本地/云端各自的原因会拼进 `reason`），不会白屏或抛未捕获异常，`detect()` 永不 reject。
- `parseReceipt(text)` 输出 `{amount, merchant, date, payMethod, confidence, dateWarn}`：
  - 命中「实付 / 支付金额 / 合计」等标签 + 完整日期 → `high`
  - 只命中金额标签 → `medium`
  - 金额靠「取最大值」猜测 → `low`（UI 提示「识别可能不准，请核对金额」）
  - 完全无金额 → `{ok:false, reason:'未识别到金额'}`，引导手动录入
  - 解析出的日期早于「今年 − 1 年」时**保留原值但降一档置信度**，并把 `dateWarn` 显示成「识别到的日期较早，请核对」
- 3 份演示样例的日期在**访问时按当天现算**（`SAMPLES` 是 getter），不会因为写死往年日期导致「确认入账后看板支出没变化」；
  确认卡的日期输入框同时带 `min`（今天 − 365 天）与 `max`（今天）。
- 确认卡的金额 / 分类 / 备注 / 日期都可改，确认后**走既有入账与冷静期流程**（高价情绪型消费仍会被拦截）。

### 11. 理财专家模式（核心附加能力）

`coach.js`（`window.AJ.coach`）提供三层能力，全部本地计算、零网络依赖：

**① 记账后主动建议 —— 「💡 理财专家说」卡片**

`adviceForBill(bill, alt)` 在 `reportCommitted()` 里被调用，命中以下任一条就出卡（**硬性 ≤50 字**，超出自动裁剪）：

| 触发条件 | 优先级 | 示例文案 |
| --- | --- | --- |
| 高溢价品牌（命中平替词典，`alt.save > 0`） | 1 | 试试三食堂现磨咖啡（10元），本周少喝两杯更香。 |
| 冲动消费（`motivation === '情绪'` 或 `want === true`） | 2 | 先加购物车晾 48 小时，两天后还想买再找我记。 |
| 娱乐类支出（`category === '娱乐'`） | 3 | 校园影院、免费展览也香，娱乐预算省着点造。 |

普通刚需餐食不出卡，避免打扰。收入账单不出卡。

**② 场景问答 —— 「怎么省钱 / 怎么赚钱」**

`localCommandName()` 识别这两类问句（含「如何省钱 / 省钱攻略 / 搞钱路子」等变体），本地直接作答，不走云端：

- **省钱**：食堂平替外卖、拿铁因子、二手真香、白嫖资源、每周复盘，5 条校园场景具体建议；
- **赚钱**：勤工俭学、技能变现、闲置回血、奖学金、竞赛奖金，附「先交钱的兼职都是骗子」防骗提醒。

**③ 剁手冷静法 —— 「我想买 XX」时先别急着记账**

`isWantBuy(text)` 识别购买意图（强意图必须位于句首，且负向意图「不想买了」、已完成购买「买了…15」不误触发），随后在聊天里走三步问答：

```
Q1 买它的核心原因？  真的需要 / 就是想要 / 犒劳自己 / 别人有我也要
Q2 买来后使用频率？  每周都用 / 偶尔用用 / 说不定吃灰
Q3 这笔钱对你来说？  轻松拿下 / 要掂量一下 / 咬牙 / 分期
```

`coolingVerdict(answers)` 按 0-6 分给结论：≥5 分「✅ 可以买（记得比价）」、3-4 分「⚠️ 建议晾 48 小时」、≤2 分「🛑 建议先不买」。
结论卡提供两个出口：**「帮我记下这笔」**（直接入账，标记情绪消费，不再二次弹冷静期）与 **「先不买了」**（金额计入 `savedMoney` 成就）。

**④ 「理财专家」Tab（底部导航第四个，桌面端顶栏 🎓 入口）**

- **专属建议**：`personalTips(state, ov)` 基于本周期账单动态生成 —— 冲动消费笔数、高溢价消费可省金额、恩格尔系数、储蓄率、应急金、花钱速度超前比例，每条给出下一步动作；账本健康时给正向反馈。

| 说明 | `about` | 100 条从哪来、金额怎么算、三个标签含义、红线 | 图谱（吸收原「数据说明」页签的内容） |

**「今天」是怎么把两个模块并到一起的**

`app.js` 的 `savingsTodayHtml()` 先取雷达当天的品牌活动（`DEALS.dealsOn(dealsNow())`），
把这些品牌名写进 `ctx.excludeNames`，图谱侧再按这份名单排除（`savings.js` 的 `excludeNames`）。
所以海底捞 / 必胜客 / 蜜雪冰城这类「当天两边都有」的品牌，在「今天」里只出现 **1 次**——
两个模块说同一件事，会让用户误以为是两笔不同的机会。
雷达活动在「今天」里复用图谱的卡片 UI 渲染（`radarAsEntry()`），但**不提供打卡**：
它是活动信息，不是可执行动作；常驻优惠（`type === 'always'`）则收成一行小药丸。

**为什么合并**：并排两个顶栏按钮既占地方、也分不清谁解决什么问题。
现在只剩一个入口 + 一张二级页签栏，页签名本身就是「今天 / 14 天日历 / 比价计算器 / 图谱 / 大全 / 省钱账 / 说明」，
不用再先判断「该点哪个」；雷达侧 2 个页签 + 图谱侧 5 个页签仍然各司其职，只是同住一个面板。

**① 真实日期算法（不靠记忆、不靠联网）**

按《广轻大南海北区优惠日历》落地 8 个**校区真实点位**：肯德基（校门口商业街）每周四、麦当劳（阳光广场）每周一 13.9 元随心配、
瑞幸 / 库迪（阳光广场）每周二 9.9 元两杯，另有赵一鸣零食、尊特优选（第二饭堂三楼）、校内便利店（各饭堂旁）、
润泰超市（正门斜对面 150 米）、宿舍楼下小卖部 5 家常驻点位。
每家都带「地点 + 优惠内容 + 理财专家建议」，全部由 `Date.getDay()` / `datetime.weekday()` 直接算：指定任意日期都能算出「下一次是哪天、还有几天」，
不会因为模型记错、活动页改版而过期。大促（双11 / 双12 / 年货节 / 38节 / 618 / 开学季）按固定月日滚动计算。

产出两份东西：
- 面板里「14 天日历」逐日列出哪天有活动；
- 底部 **下载真实商家日历.csv**，内容由代码生成（Excel 直接打开，日期是真的，不是手抄的）。

**② 比价口径引擎（前端 `deals.js` 与后端 `deals_engine.py` 同一套规则）**

输入各平台报价（价格 / 规格 / 运费 / 券 / 需买几件），输出：

```
到手价 = 标价 × 需买件数 + 运费 − 券
折合单价 = 到手价 ÷（规格数量 × 需买件数）
```

关键判定（这些地方最容易算错、也最容易糊弄人）：
- **规格不同只能比单价**：`12 包 12.99` vs `24 包 42.23`，差的是单价不是总价；
- **「需买 N 件」不能当单件价**：`99 元 × 2 件 = 198 元`，跟单件 89 元比会说成「贵 109 元」；
- **规格口径对不上就拒绝下结论**（`mixed` / `comparable=false`）：宁可说「比不了」，不硬凑一个「最便宜」；
- 单位折算支持 ml / g / kg / 斤 / mAh / 包 / 抽 / 提 / 瓶 / 罐 / 袋（`两瓶装500ml`、`280抽6提`、`10000mAh` 都能读）。

**③ 大模型工具调用（`deals_api.py`）**

`POST /api/deals/ask` 注册了三个工具（`get_today_deals` / `get_deal_calendar` / `compare_prices`），
模型先调工具拿**真实日期和真实计算结果**，再组织语言——不是让它凭记忆说「周四有活动」。
没配 `LLM_API_KEY` 时自动降级为本地确定性回答（结论一样，只是没有自然语言润色）。

| 接口 | 作用 |
|---|---|
| `GET /api/deals/today?date=2026-10-24` | 当天活动 + 双11 倒计时 + 下一次疯狂星期四 |
| `GET /api/deals/calendar?days=14` | 未来 N 天逐日日历 |
| `GET /api/deals/calendar.csv` | 下载真实商家日历 CSV |
| `POST /api/deals/compare` | 比价（到手价 / 单价 / 可比性 / 排名 / 时机 / 预算） |
| `GET /api/deals/quote?item=充电宝&price=89&budget=100` | 这个价属于哪一档 + 该不该等大促 |
| `POST /api/deals/ask` | 大模型 tool-calling 入口 |

启动：`python deals_api.py`（默认 8010，文档 `/docs`）。

**④ 比价结果「点开就能到商品页」（不再让用户自己复制链接）**

比价页里三个地方都能直达商品页，全部是真 `<a href target="_blank">`（`rel="noopener noreferrer nofollow"`），
链接统一过 `safeHttpUrl()` 白名单（只放行 `http/https`，其余协议静默丢弃）：

| 位置 | 元素 | 行为 |
| --- | --- | --- |
| 真实搜索结果行 | 标题本身 `<a class="rs-title">` + 副信息行末尾「去逛逛 ↗」`<a class="rs-lnk">` + 行尾「打开」`<a class="rs-open">` | 三个入口都指向同一条报价的商品页 |
| 比价表单每个报价行 | 可编辑的商品链接输入框 `<input class="dc-link">` + 右侧「打开」小按钮 `.dco-go` | 按钮读**输入框当前值**跳转（`openDealRowLink()`），所以用户可以先把链接换成自己要的页面再打开；链接为空时按钮**置灰禁用**，悬浮提示「这一行还没有商品链接，先粘贴一个」，输入框 placeholder 为「粘贴商品链接（可留空）」 |
| 比价结果表每行 | 「看商品 ↗」`<a class="dc-td-link">` | 指向该行报价的链接；输入框里的链接改完（失焦）会静默重算一次，结果表的链接跟着变 |

「填入比价」会把这条报价的**平台、价格、规格、商品链接**一起带进比价表单
（`fillRealOffer()`：`row.platform` 取商品**真实所在平台**，保证下拉框能选中；`row.link` 取该报价的链接）。

**链接口径（诚实写清楚，不含糊）**

| 平台 | 链接形态 | 说明 |
| --- | --- | --- |
| 网易严选 | `you.163.com/item/detail?...` | **直连商品页** |
| 当当 | `product.dangdang.com/...` | **直连商品页** |
| 京东 / 天猫 / 淘宝 | `cu.manmanbuy.com/discuxiao_xxx.aspx` | 由「慢慢买比价」聚合而来，是**中转页**：先打开中转页（可能先过人机校验），正常浏览器会自动跳到商家商品页；没跳成就点页内「去购买」兜底 |

平台 chip 标的是**商品真实所在的平台**（京东 / 天猫 / 淘宝 / 网易严选 / 当当），
不是聚合站名——否则用户不知道「这个价是谁的」。
所以链接口径也分两类：网易严选 / 当当一点就到，京东 / 天猫 / 淘宝要多走慢慢买中转这一跳；
**链接框可以由用户自行替换成商家直链**（`.dc-link` 是可编辑输入框，不是只读文本）。
比价表单里每个链接框下方还有一行小字（`.dl-link-hint`）标注这条链接的来源：慢慢买中转页会写明
「链接来自慢慢买比价页（不是『京东』直链，可自行粘贴商家商品链接替换）」，严选 / 当当直链则写明
「网易严选直连商品页」；这行小字随输入**实时更新**（`syncDealLinkRow()`），链接为空时「打开」按钮置灰禁用。
比价结果区里也如实写着价格与销量是抓取当时的页面展示值、会随促销与库存变动。

**⑤ 刻意不做的事（写进代码注释，也写进面板的「说明」页签）**

- **不编价格**：没有真实报价时，只给「品类价格带」参考 + 明确告诉用户还差哪个平台的价；
- **不硬下结论**：规格口径对不上（`mixed`）就明说比不了；
- **不承诺最低价、不做返利导流**：给的链接就是商品页地址本身（带 `nofollow`，不带任何推广参数），
  也不写死任何平台的实时价——真下单前以商家当期页面为准。

> 注：抓取真实搜索结果走的是**本机后端**（`deals_api.py` 的 `/api/deals/search` → `deals_scrape.py`），
> 不是浏览器直接抓电商页；没起后端时面板里用的是 `deals.js` 内置的快照 `DEALS.REAL_SEARCH`，
> 并在界面上标注抓取时间与页数，不拿旧数据冒充实时数据。

想接别的价格源？在 `.env` 配 `PRICE_API_URL` / `PRICE_API_KEY` / `PRICE_FIELD_MAP`，
把官方接口返回的字段映射进同一个比价引擎即可，计算逻辑不用改一行。

### 13. 省钱图谱（100 条动作 + 打卡省钱账）

**和省钱雷达的分工**：雷达回答「**哪天**有活动、**谁**更便宜」；图谱回答「**具体怎么操作**才省」。
两者仍是两个独立模块（`deals.js` / `savings.js`，数据形态和失效条件完全不同：一个是日期规则，一个是人的动作），
只是**入口和面板已经合并成一个「省钱助手」**（见 §12）：雷达侧占 2 个页签（14 天日历 / 比价计算器），
图谱侧占 5 个页签（今天 / 图谱 / 大全 / 省钱账 / 说明），同一张二级页签栏里切换。

**入口**：顶栏「💰 省钱」统一面板 / 看板「🛒 省钱雷达」「💡 今天怎么省」两张直达卡 /
简洁版底部「省钱助手」Tab 与「我的 › 省钱助手」（**简洁版是独立页面，不是弹窗**）/ 聊天里说
「今天怎么省」「省钱图谱」「所有省钱大全」「省钱大全」「我的省钱账」。
（细节：两张看板卡的「查看」都落到同一个面板；面板内是一张 7 页签的二级页签栏，没有一级分段。）

**两套 UI 的呈现方式不同**：完整版点顶栏「💰 省钱助手」弹出面板（遮罩 + 圆角浮层，`Esc` / 点遮罩关闭）；
简洁版底部有独立的「省钱助手」Tab（**7 格**：记账 / 明细 / 预算 / 省钱助手 / 搭子 / 理财专家 / 我的），进去是**整页区块、不是弹窗**——
同一份 `#saveHubSheet` 由 `mountShellPanels()` 搬进 `#spSaveBody`（切回完整版时再搬回遮罩），
所以没有遮罩、没有关闭按钮，靠底部 Tab 离开（不打断当前二级页签的选择）。

**图谱侧的五个页签**

| 页签 | 内容 | 关键约束 |
|---|---|---|
| 今天 | 三个数字（本周期省下 / 本周期打卡 / 累计省下）+ 今日清单 + 今天已打卡（可撤销）**+ 雷达当天的品牌活动**（见 §12 的合并规则） | **今天用不了的条目绝不进清单**：周一的「周四肯德基」不许出现；雷达侧同品牌当天不再重复出现 |
| 图谱 | 100 条全量，搜索 + 10 分类筛选 + 每条展开 10 个字段 | 分类与搜索是**叠加**关系；搜索结果高亮关键词 |
| 大全 | **所有省钱大全**：100 条压成一行一条的速查索引（按 10 类分组） | 「一眼扫完 100 条」的场景用，不占一屏一条；点任一行跳到图谱并自动展开详情 |
| 省钱账 | 累计省下 / 总次数 / 本周期次数 + 分类条形 + 最近 12 条打卡 | 累计**不随预算周期清零**，与「本周期」分开算 |
| 说明 | 100 条从哪来、金额怎么算、三个标签含义、红线 | 面板里直接披露存储键名，用户能自己核对 |

**「大全」和「图谱」为什么都要有**：图谱是「读」的（一条占一屏、10 个字段），大全是「扫」的
（一行一条、标题 + 省多少 + 何时能用）。100 条里找自己今天能干的，先扫再读；两者共用同一份数据，
索引行点进去会带着分类与详情一起落到图谱页签，不需要用户再找一遍。

**所有省钱大全的 Markdown 导出**：大全页签工具条上一键导出 `.md`，含 100 条全量（做法 / 门槛 / 坑在哪 /
数据来源）+ 我的打卡次数，可贴进群、笔记或交给别的工具。纯前端拼字符串，不联网。

**金额怎么来的（`save.type` 四型）**

| 类型 | 含义 | 数量 | 说明 |
|---|---|---|---|
| `fixed` | 固定省额 | 1 | 原文给了明确差价 |
| `ratio` | 折扣比 | 5 | 有原价基准才乘；**缺基准返回 `null` 而不是 0**（0 会让人以为这条没用） |
| `range` | 区间取中位 | 89 | 原文只说「省几十」这类 |
| `none` | 无法量化 | 5 | 保温杯、图书馆：照样能打卡，但不进金额累计 |

**三个诚实性标签（`certainty`）**：无标签 = 规则稳定；`力度常变` = 会员日 / 百亿补贴；`以你学校为准` = 依赖具体校区门店（16 条）。

**⚠️ 大促 / 年卡型条目（`save.once`）金额记 0**

双 11 的「省 100-500」是**整场活动的总额**，不是「今天点了这一下省了多少」。
若校验时直接入库，点一次「双 11」就往省钱账里加 ¥300，累计金额瞬间失真、分类条形被促销类霸榜。
所以这类条目只计打卡次数、金额记 0，卡片上标「大促可省 / 全年可省 / 一次性省」，省钱账里也会说明有几条只计次数。

**打卡存储：独立键 `ai_jizhang_savings_v1`**

不并进 `ai_jizhang_v1` 的三个理由：

1. 主账本一动 `normalizeState()` 就要重跑全套账本回归，风险大；
2. 省钱记录损坏时**只重置自己**，绝不能让用户丢掉真实账单（坏 JSON → 清空 + 提示一次，账单不受影响）；
3. 「买对省 X」和冷静期「拦下 Y」是两个概念，合并显示会让用户以为同一笔省了两次。

记录结构 `{ id, date, saved, manual, at }`；归一化规则：非法 id / 非法日期丢弃、同 `(id,date)` 去重、
`saved` 非法按 0、总量上限 2000 条（超出丢最旧）。第二次点同一条目即撤销（幂等）。

**今日清单的硬规则（比排序更重要）**

```
① 有 trigger 但今天不命中  → 直接排除，不参与排序
② 命中今天的条目优先，受 limit（5）限制
③ 常驻条（trigger=null）只做补位，最多 3 条
排序：score ↓ → 可省金额 ↓（once 型视为 -1）→ id 字典序 ↑
```

最后一级用 `id` 字典序是为了**同日期两次渲染顺序必须完全一致**——否则「可复现」无法验收。

打分：`40 命中今天 + 25 撞本周期 Top1 分类 + 20 该分类有支出 + 15 预算紧张 + 10 力度稳定 + 5 能算出金额`。
所以「你 62% 的钱花在餐饮」会真的把餐饮类动作往前推，这是**账本联动**的落地点。


### 13.5 买谷指南（省钱图谱第 11 类「吃谷避坑」+ 5 个能动手的工具）

**为什么单独做**：吃谷是学生群体里最典型的高频冲动消费 —— 单笔金额不大，但频率高、决策快、
商家信息不对称严重（祖国版 / 尾单 / 假海景谷）。已有的「省钱图谱」是给**通用消费动作**用的
（奶茶、打印、周四肯德基），吃谷的坑是**另一类**：不是「怎么买便宜」，而是「怎么不买错、不被骗、不超支」。
所以它作为第 11 个分类独立存在，条目只做知识沉淀，真正有用的是挂在条目上的**五个交互工具**。

**入口只有一个**：省钱图谱 → 吃谷避坑分类。**不做**独立的理财专家卡、也不做独立入口 ——
入口越散越没人用，统一挂在已经存在的图谱分类下最自然。

**五个工具（`gu.js`，全部是纯逻辑 + UMD，Node 可单测）**

| 模块 | 做什么 | 交互形态 |
|---|---|---|
| ① 谷圈黑话速查 | 34 条高频黑话（吧唧 / 立牌 / 流麻 / 海景谷 / 捆 / 肾 / 跑单 / 祖国版…），每条给**释义 + 一句避坑** | 搜索框边打边筛（搜词也搜释义）；点词条展开避坑提示 |
| ② 买谷渠道分级 | 绿（闭眼入）/ 黄（谨慎）/ 红（别碰）三档，**每项都带「怎么验」** | 三档色块清单，红档写明「私转 / 低于市价 30% 的海景谷」 |
| ③ 拼团防跑路清单 | 跟团前必查 5 项（团长 ≥3 次成功开团 / 平台担保 / 公开凭证物流 / 书面发货与退款 / 规模 ≤50 且预售 ≤6 月） | 5 个可勾选项 + 进度条；**全过**才出「可以跟团」，勾选状态落盘 |
| ④ 盲盒抽赏冷静器 | 3 问自检（热冷查了吗 / 概率公示了吗 / 抽到不想要愿花精力出二手吗） | 逐题作答，给「可以抽，但先设好吃谷罐额度」或「先别抽，去闲鱼收确认款」 |
| ⑤ 吃谷罐 | 月度专项额度隔离：设 ¥50 后，买谷只从这个数里出 | 三格统计（已用 / 额度 / 还能花）+ 进度条；**超额直接拦住**（不是提醒） |

**为什么额度是「拦」不是「提醒」**：吃谷超支的特点是「当时不觉得贵，月底才发现吃土」。
提醒式设计在冲动当下会被无视，所以吃谷罐做的是**硬闸** —— 额度外的金额记不进去，
想花就先把额度调高（调高这一步是冷静的、有摩擦的，正好过滤掉冲动）。

**入口放在条目详情里，不另开页签**：用户是「为了这一条动作」才点进来的，就地长出工具最省事。
面板挂载点由 `guToolPanel(entry)` 按条目 id 分发（`gu.glossary.101` → 黑话速查，`gu.channel.102` → 渠道分级，
`gu.group.103` → 拼团清单，`gu.gacha.104` → 冷静器，`gu.budget.105` → 吃谷罐）。

**存储隔离**：独立键 `ai_jizhang_gu_v1`，与主账本、存钱罐、图谱打卡记录完全解耦；
金额一律用「分」的整数（避免 0.1+0.2 浮点误差）；存档坏了只重置吃谷罐，绝不动真实账单。
`app.js` 侧用与存钱罐同构的**空替身**模式接入（`GU.missing` 时工具箱入口自动隐藏，其它功能零影响）。

**聊天侧的联动**（与图谱共用一套知识，不重复实现）：

- 说「买谷指南 / 吃谷攻略」→ 弹出 5 问速览卡（怎么判断正版 / 拼团防跑路 / 盲盒能不能抽 / 闲鱼收二手 / 热谷冷谷怎么查）；
- 消息里出现二次元词（吧唧 / 立牌 / 盲抽 / 拼团 / 出谷…）且**不像记账句** → 按关键词给对应劝导（盲抽劝去收确认款 / 拼团劝只走担保 / 出谷鼓励记成收入）；
- 记账后若命中「购物 + 备注含谷」→ 追加一条正版确认提示（问是不是官方渠道）。

**验证**：`node _test_gu.js` 120 项断言（纯函数与存储契约）；`python _qa_gu.py` 32 条真机断言
（Chrome CDP **真实鼠标点击**：搜词、勾选、答题、设额度、记一笔、超额拦截、刷新后落盘）；
`python _qa_smoke.py` 7 条交付物冒烟；`python _qa_note_gu.py` 11 条备注链路断言（「盲盒 199」→ 先不买 →
心愿标题必须是「盲盒」）。暗色对比度脚本 `_qa_gu_dark.py` 已不在磁盘，重建时注意：**切主题不能直接
`setAttribute('data-theme')`**，要走 `Emulation.setEmulatedMedia` 模拟系统配色偏好。

**暗色验证的一个坑（值得记）**：切主题不能直接 `documentElement.setAttribute('data-theme', 'dark')` ——
应用自己的 `applyAppearance()` 会在稍后（init / 改设置 / 系统主题变化）用 `resolveTheme()` 覆盖它，
而 `resolveTheme()` 在「跟随系统」时读的是 `matchMedia('(prefers-color-scheme: dark)')`。
结果是脚本「切了暗色」，截图拍到的其实还是浅色，**两套对比度数据一模一样就是征兆**。
正解是用 CDP 的 `Emulation.setEmulatedMedia` 模拟系统配色偏好，再让应用自己走一遍主题解析路径。

### 14. 账单流水：收起 / 展开 + 筛选器的时间维度

看板「账单流水」卡片与简洁版「明细」屏共用同一套折叠与筛选语义（`app.js` 的渲染层 + `billfilter.js` 的纯函数层）。
筛选抽屉（`#billFilterMask`）两版共用同一个面板，筛选条件也共用同一份状态。

**① 收起 / 展开：默认只展开最近 2 个日期组**

| 项 | 实现 |
| --- | --- |
| 折叠阈值 | `BILL_COLLAPSE_GROUPS = 2`（`app.js`）：按**日期组**算，不是按条数——组头与组内条目永远成对出现，不会出现「孤零零一条挂在组头下面」 |
| 按钮 | 完整版 `#btnBillExpand`、简洁版 `#btnSpBillExpand`；文案在「展开全部 N 笔」/「收起」之间切换（N = 当前筛选后的总笔数） |
| 自动隐藏 | 日期组数 ≤ 2 时按钮 `hidden`，不出现「点了没反应」的按钮 |
| 状态 | 完整版 `billListOpen`、简洁版 `spListOpen` 各自独立，互不影响 |
| 组头文案 | 「今天 / 昨天 / M月D日」，跨年时补上年份 |

**② 标题右侧两个按钮 + 标题下方一行范围提示**

- 完整版卡片标题右侧：`展开/收起` + `筛选`（`.btn-filter` 胶囊，漏斗图标 + 文字；筛选生效时变实心绿底「筛选·N」）；
  简洁版「明细」屏的这两个按钮在页头右侧（`.sp-head-tools`）。两版的「筛选」按钮共用同一个抽屉与同一份筛选状态。
- 标题下方独立一行范围提示（完整版 `.bill-scope` / `#billScopeHint`，简洁版 `.sp-scope` / `#spScopeHint`），
  如实显示当前范围与笔数：无时间条件时显示「全部 · N 笔」；有时间条件时显示「10月22日–10月28日 · 9 笔」，
  只填一端则显示「10月28日 起」/「截至 10月28日」。
- 之前标题写死「本月账单流水」但实际渲染的是全部账单，标题与内容对不上；
  现在标题只叫「账单流水」，到底看到哪一段交给范围提示行说。

> 两版取数范围不同：**完整版渲染全部账单**；**简洁版「明细」只渲染当前月份**（页头有月份切换 `‹ 本月 ›`）。
> 折叠阈值、筛选语义、范围提示文案完全一致。

**③ 筛选抽屉新增「时间范围」区**

| 元素 | 实现 |
| --- | --- |
| 快捷胶囊 | `#bfTimeQuick` 里 4 个 `.bf-qcap`：`今天` / `近 7 天` / `近 30 天` / `本月`（`data-bf-quick="today\|7d\|30d\|month"`） |
| 快捷区间口径 | 近 7 天 = 今天往前 6 天 ~ 今天；近 30 天 = 今天往前 29 天 ~ 今天；本月 = 当月 1 号 ~ 当月最后一天 |
| 自定义起止 | 两个 `<input type="date">`：`#bfFrom` / `#bfTo` |
| 区间性质 | **闭区间** `[from, to]`；两个都空 = 不限日期 |
| 填反了 | `from > to` 自动对调（`billfilter.js` 的 `normalize()`），不会一条都筛不出来 |
| 非法日期 | 非法格式（`2026/01/01`、`2026-13-01`、2 月 30 日）一律兜底成「不限」，绝不抛异常 |
| 手动改日期 | 手动改了日期框，4 个快捷胶囊全部熄灭（因为已经不属于任何一档）；点回胶囊才重新高亮 |
| 「不限」按钮 | 时间范围区的 `data-bf-all="time"`：清空起止日期框与胶囊高亮 |

**④ 组合语义**

- 时间范围与分类 / 金额 / 备注是 **AND** 关系（`billfilter.js` 的 `match()`）；
- 时间维度单独算一维，筛选按钮角标「筛选·N」的 N 由 `activeCount()` 给出：
  支出分类 / 收入分类 / 金额区间 / 备注关键词 / 时间范围，**最多 5 维**；
- 列表上方的 `.bf-bar` 摘要条把各维度拼成一句话（`·` 分隔），时间条件显示成「10月22日 ~ 10月28日」，
  右边跟「N 笔」和「清除」；
- **日期缺失的账单在启用时间筛选时一律排除**（否则会混进不在区间内的记录）；
- 简洁版顶部的「本月支出 / 本月收入」**永远显示全月真实值**，筛选只影响下方列表——
  否则筛出「餐饮」后本月支出会缩水，容易被误读成真的只花了这么多。

**为什么加时间维度**：原来只有分类 / 金额 / 备注，「上周奶茶花了多少」「这个月超支了吗」只能靠手动翻列表；
有了时间范围，「近 7 天」「本月」两个快捷档就能把列表直接缩到要看的那一段，
而且闭区间 + 填反自动对调，保证「填错日期」不会变成「筛不出任何东西」。

### 15. 双 UI：完整版（报表型）/ 简洁版（日常型）与按视口宽度的自动分流

两套界面**共用同一套账单数据**，切换即时生效、互不丢失。切换靠 `<body data-ui-mode="full|simple">`：
简洁版下 `body[data-ui-mode="simple"] #app { display: none; }`（`styles.css:7265`），由 `#simpleShell`
+ `#tabbarSimple` 接管；完整版反之。两套界面的**视图名不通用**（`app.js:456` `FULL_VIEWS`
= `chat/dash/goals/coach/dazai`；`app.js:459` `SIMPLE_VIEWS`
= `shome/slist/sbudget/sprofile/sai/scoach/sgoals/ssave/spiggy/sdazai`），
所以 `switchView()` 会拦掉非法视图，`applyUiMode()`（`app.js:5914`）也会在切档后把视图纠正到该档的合法默认
（`simple → shome`、`full → chat`）。

**切换入口（两处，都走 `setUiMode()`，`app.js:5973`）**

| 入口 | 控件 | 绑定位置 |
| --- | --- | --- |
| 设置面板 →「界面风格」→ **UI 类型** | `#setUiModeSeg`，两个 radio `name="setUiMode"`（`simple` / `full`） | `app.js:6180` |
| 简洁版「我的」页 →「设置」 | 2026-10-29 起残缺卡 `#spUiSeg` 已移除，改开与完整版共用的 `#settingsPage` | `app.js:3487` |

> 静态 HTML 里 `input[name="setUiMode"][value="full"]` 带 `checked`，那只是首帧占位；
> 真实勾选由 `renderSettingsPage()`（`app.js:6032` `checkRadioGroup('setUiMode', state.uiMode)`）
> 与 `renderSimple()`（`app.js:3279` `checkRadioGroup('spUiMode', getUiMode())`）按存储值纠正，
> **不要**把 HTML 里的 `checked` 当成默认值来源。

**冷启动时按视口宽度自动重算（双向）**

- **判定**：`PHONE_MAX_WIDTH = 640`（`app.js:5887`）；`isNarrowPhone()`（`app.js:5892`）先试
  `matchMedia('(max-width: 640px)')`，环境不支持时依次回退 `innerWidth` → `documentElement.clientWidth`
  → `1024`（按非窄屏兜底）。**只看视口宽度，不看 UA、不看触屏能力** —— 这样评委在桌面浏览器拖窄窗口
  或用 Chrome 设备模拟，都能复现同一分支。
- **重算点**：`init()` 里 `loadState()` 之后、`applyUiMode()` 之前（`app.js:14768-14787`）。
  只要 `state.uiModePicked` 为 `false`（从没手动选过），就按**当下**视口宽度算出目标档
  `var wantMode = isNarrowPhone() ? 'simple' : 'full';`，与当前 `state.uiMode` 不同才改。
  **双向**：窄屏 → 简洁版，宽屏 → **回到完整版**。`uiModePicked === true` 时整段跳过，永远以用户选择为准。
- **提示**：只有**被重算带进简洁版**这一次才弹（`autoSimple` 为真时 `setTimeout(…, 0)` 弹一句
  「窄屏已默认进入简洁版（设置 → 界面 可切回完整版）」）；被重算**回**完整版不弹（否则桌面用户会看到一句
  莫名其妙的「窄屏…」）。手动切换由 `setUiMode()` 自带的 toast 负责，不重复弹。
- **默认落点**：`app.js:14812` —— 简洁版 `shome`（记账首页），完整版 `chat`（聊天）。
- **只在冷启动评估**：刷新 / 重新打开页面才重算，运行中拖窗口改宽度不会实时切换（见 §七 26）。

**已实测的行为表**（`_shot/verify_ui_default.js`：无头 Chrome CDP + `Emulation.setDeviceMetricsOverride` 覆盖视口宽度；标「全新用户」的行每次先清 localStorage）

| 场景 | 结果 |
| --- | --- |
| 全新用户 @ 390px（手机典型宽度） | `data-ui-mode=simple`，落在 `shome`，`#tabbarSimple` 可见，弹一次「窄屏已默认进入简洁版…」 |
| 全新用户 @ 1280px（桌面） | `data-ui-mode=full`，落在 `chat`，无提示 |
| 全新用户 @ 640px | 判为手机 → `simple` |
| 全新用户 @ 641px | 判为桌面 → `full` |
| **窄屏用过（从未手动选过）后再换成 1280px 打开** | **自动重算回 `full`，且不弹提示**（`uiModePicked` 仍为 `false`） |
| **1280px 启动后再换成 380px 打开** | **自动到 `simple`，弹一次提示** |
| 窄屏下手动选「完整版」后刷新 | 仍是 `full`（`uiModePicked=true` 已落盘） |
| 宽屏下手动选「简洁版」后刷新 | 仍是 `simple` |
| 窄屏点底部「明细」Tab | 正常切到 `slist`，简洁版外壳不是空壳 |

> `savedMoney` / `blockedCount` 是需求要求的成就数据，属于对基础结构的扩展字段；

**两个 UI 字段的取值口径**

| 字段 | 默认 / 归一化 | 谁会改它 |
| --- | --- | --- |
| `uiMode` | 新账本种子 `'full'`（`app.js:754`）；读档时非 `'simple'` 一律归一成 `'full'`（`app.js:678`） | `setUiMode()` 手动切换（`app.js:5976`）；**自动分流**在每次冷启动时按视口宽度**双向重算**（`app.js:14776` —— 窄屏写 `'simple'`、宽屏写回 `'full'`） |
| `uiModePicked` | 新账本种子 `false`（`app.js:756`）；老账本没有这个字段时读成 `false`（`app.js:681` `s.uiModePicked === true`）——即「没选过」，才会被自动分流接管 | **只有** `setUiMode()` 会置 `true`（`app.js:5979`）；自动重算**不写**它，所以「还没选过」状态会一直保留，下次冷启动仍会重算 |

> 自动重算是**幂等且与落盘无关**的：它每次冷启动都按当下宽度重算一遍
> （`app.js:14773-14779`），所以上一次在窄屏落盘的 `simple` 不会把用户锁死 ——
> 换个宽度打开就会被算回对应的档。真正能锁死 `uiMode` 的只有手动选择（见 §三 15、§七 26）。

## 五、关键设计决策

1. **中文数字必须带单位或动词或位于句末两位以上**，否则 `三食堂`、`一双鞋` 会被误判成金额。
2. **金额切段代替连接词切分**：一句话里出现 N 个金额就切 N 段，天然支持「打车 15 和奶茶 12」。
3. **日期上下文继承**：「昨天打车15，奶茶12」第二笔没有时间词，继承第一笔的「昨天」。
4. **冷静期把 `want` 也算作非刚需**：需求原文的判定是「!刚需(情绪型)」，服装鞋包虽然动机记为
   「刚需 + want:true」，但从产品意图上属于冲动消费，因此一并纳入拦截，避免「¥299 的卫衣」绕过提醒。
5. **localStorage 失败降级**：读写全部 `try/catch`，失败后切内存存储并在顶部显示「当前为临时模式，关闭页面数据不保留」。
6. **周期重置用独立的 `budget.cycleStart`，不改写 `payday`**：这样「恢复按发钱日算」只要清空一个字段，
   而且 v1 的 `getCycle(today, payday)` 调用方一行都不用改（等价性用 720 组用例回归）。
7. **导入默认只分析、不写账本**：并入账本必须用户主动点击 + 二次确认，且导入时把**支出方向的**「转账 / 还款」标记为
   `excluded`，因为给室友转账、还花呗不是消费，混进支出会让所有占比失真。
   **收入方向的转账要计入**——爸妈打生活费在账单里就是「交易类型=转账」，排掉它会让收入显示 0；
   但会打 `transferIncome` 标记并在状态栏提示，把「是不是本人账户互转」交回用户判断。
8. **全项目只有 `ocr.js` 出现 `fetch`**，并且只在「用户配了云 OCR 凭据 + 主动点识别 + 有图片」三条同时成立时才执行；
   默认路径（原生识别 / 演示样例）零网络，保证断网也能演示。
9. **周末 vs 工作日比的是「日均」**：周末天数少、总额天然低，直接比总额会得出「周末更省」的错误结论，
   所以两边都除以「该桶内有记录的天数」。
10. **窄屏判定只看视口宽度（≤ 640px），不看 UA、不看触屏能力**：`PHONE_MAX_WIDTH = 640`（`app.js:5887`）。
    用 UA 判「是不是手机」在演示现场不可复现 —— 评委在桌面 Chrome 上拖窄窗口、或开 DevTools 设备模拟，
    UA 都不变，就会走不到被演示的那个分支。只看宽度则「所见即所得」，代价是 iPad 竖屏（768px）算宽屏、
    **会被重算回完整版**（哪怕上次是在窄屏下用的），这是刻意的可复现性取舍，不是漏判（同时记在 §七 26）。
11. **自动分流是双向重算，`uiModePicked` 让手动选择永远优先**：`init()` 里只要 `uiModePicked` 为 `false`，
    就按当下视口宽度算出 `wantMode = isNarrowPhone() ? 'simple' : 'full'` 并对齐（`app.js:14773-14779`）——
    **窄屏进简洁版、宽屏回到完整版**，不做单向的「只往简洁版倒」。因此
    ① 没选过的人怎么换设备 / 换窗口宽度都会被算回对应档，一次环境判定不会变成永久决定；
    ② 一旦用户在设置面板的「界面风格」控件里显式选过（选简洁版或完整版都算，`setUiMode()` 置
    `uiModePicked = true`，`app.js:5979`），整段重算被跳过，**以后无论宽窄都以他的选择为准**。
    （2026-10-29 起简洁版残缺卡已移除，该控件只剩设置面板一处。）
    自动重算**不写** `uiModePicked`，这是两条规则能共存的关键。

## 七、已知限制

1. **周期长度固定按发钱日推算**：`getCycle` 在未传 `cycleLen` 时，结束日为「次月发钱日 - 1 天」，
   遇到 2 月等短月份时周期会短几天（这是正确的日历行为，但演示时请留意）。
2. **发钱日限制在 1-28**：避免 29/30/31 号在小月里不存在的问题。
3. **语音输入依赖浏览器**：仅 Chrome / Edge 支持 `webkitSpeechRecognition`，Safari 与 Firefox 会置灰。
4. **CSV 三连下载**：部分浏览器的「多文件下载」拦截策略可能只放行第一个文件，需要允许本站点下载多个文件。
5. **NLP 不是大模型**：基于词典与规则，能覆盖常见校园记账句式。认不出金额时**不再整句否定**——
   而是先判意图（记账 / 查询 / 问方法 / 求建议 / 改删 / 闲聊）、再按缺失的槽位只问那一个，
   并按「L2 金额按钮 → L3 表单 → L4 示例 → L5 人工出口」逐级升级，同一句提示绝不重复出现。
   具体规则见第八节。
6. **恩格尔系数默认不预警**：演示数据的餐饮占比约 32%，属于健康区间；想现场看橙色预警，多记几笔餐饮即可。
7. **无多用户/云同步**：数据只在本机 localStorage，符合「断网可演示」的参赛要求。
8. **云 OCR 可能受浏览器跨域限制**：`file://` 或普通网页直接调腾讯云接口可能被 CORS 拦下，
   失败时会给出提示并引导使用示例小票或手动录入，不会白屏；需要稳定云识别时请用本地服务器 + 腾讯云控制台配置允许的来源。
9. **Windows 桌面 Chrome 不支持 `window.TextDetector`**：因此**不配置云 OCR 时，截屏识别只能走「示例小票」或「手动录入」**，
   上传自己的截图点「开始识别」会得到一条明确的「这台设备没有可用的文字识别能力」说明 + 三个出口按钮
   （用示例小票演示 / 配置云 OCR / 手动录入）。**应用不会拿示例数据冒充识别结果**：`auto` 模式没有任何能力时
   返回 `ok:false, source:'none', text:''`，内置样例只在用户主动点「示例小票」时出现，且届时若存在用户图片，
   预览图会被收起并显示「这是内置示例，不是你上传的截图」的黄色提示。
10. **导入账单默认不入账本**：只有点「把导入记录并入账本」并二次确认后才写入，且并入后会立即改变预算统计与日均。
11. **GBK 解码依赖浏览器 `TextDecoder('gbk')`**：Chrome / Edge 支持；Safari 部分版本不支持，会落到「无法识别文件编码」，
    可以把文件另存为 UTF-8 再导入。
12. **截图识别不是万能**：菜单、聊天记录、严重模糊的截图可能读不到金额；此时会用结构化错误提示并给手动录入入口。
13. **导入不自动去重写入**：疑似重复默认只标记，重复并入同一份文件会产生重复账单。
14. **省钱图谱的金额是估算区间，不是报价**：知识库里只有「省 30%」「省几十」这类说法，
    `range` 型取区间中位、`ratio` 型必须有原价基准才算，`none` 型直接不计金额。
    界面上从不说「最低价」，也不写死任何平台的实时价格；真下单前以商家当期页面为准。
15. **大促 / 年卡型条目只计打卡次数、不计金额**（`save.once`）：双 11 的「省 100-500」是整场活动的总额，
    记进省钱账会让累计虚高，所以金额记 0，卡片上标「大促可省 / 全年可省 / 一次性省」。
16. **省钱打卡的金额可以事后手改，但只有一个「覆盖」口径**：省钱账每条记录右侧有「改」，
    填 0~10000 之间的数即覆盖估算，`manual` 记为 `true`（导出 CSV 时「是否手动改过」列写「是」）；
    **清空输入框 = 恢复引擎估算**，`manual` 回到 `false`。这里不保留历史修改记录，也不做多次改动的审计。
17. **活动日期由本地日期算法推算**（周几 / 每月几号 / 固定月日 / 时间区间），不联网抓取，所以离线可用，
    但**商家临时改档期不会自动同步**——这也是多数条目带「力度常变 / 以你学校为准」标签的原因。
18. **深色主题的页签选中态单独补过一条规则**：`[data-theme="dark"] .atab` 的权重高于 `.atab.active`，
    会把选中页签刷成和未选中同色（账单分析的「当前账单 / 导入 CSV·Excel」两页签、省钱助手的 7 个二级页签两处都受影响）。已补
    `[data-theme="dark"] .atab.active`，改这组样式时别把这条删掉。

    这个阈值是写死的常量，想改成 3 组或 5 组要同时改 `app.js` 的这一处。
25. **启用时间范围筛选后，日期缺失的账单会被排除**（`billfilter.js` 的 `match()`）：
    账本里所有账单都有日期，所以正常情况下不会遇到；但如果将来接入无日期的记录，它们在时间筛选下不会出现在列表里。
    另外时间范围是**闭区间**，`from > to` 会自动对调，非法日期格式（如 `2026/01/01`、`2 月 30 日`）一律兜底成「不限」。
26. **窄屏默认简洁版只在冷启动评估，不是实时自适应**（详见 §三 15）：
    - 规则是**双向重算**：每次冷启动（刷新 / 重新打开）都按**当下**视口宽度算目标档（`app.js:14773-14779`
      `wantMode = isNarrowPhone() ? 'simple' : 'full'`），窄屏 → 简洁版、宽屏 → 回到完整版；
      但**运行中拖动窗口改变宽度不会实时切换**，必须刷新才生效（实时切会打断用户正在填的表单）。
    - 只要 `uiModePicked === false`，重算就不受「上一次落盘是什么」影响 —— 窄屏用过后换宽屏打开会被带回完整版。
      一旦在「设置 → 界面风格」里手动选过任意一档（简洁版/完整版都算，`uiModePicked = true`；2026-10-29 起两种模式共用这一个设置面板，无第二处控件），此后**永久以该选择为准**，不再重算。
      点「已选中」的那一档同样算显式确认（radio 已选中再点不触发 change，由 click 补标记监听兜住）。
    - 判定不看 UA / 触屏，所以 **iPad 竖屏（768px）算宽屏**、进完整版；这是刻意的可复现性取舍（见 §五 10）。
    - 静态 HTML 里 `input[name="setUiMode"][value="full"]` 带 `checked`，那只是首帧占位，
      真实勾选由 `renderSettingsPage()` / `renderSimple()` 按存储值纠正，**不要**把它当默认值来源。

## 八、意图路由与模糊兜底（一句话到底怎么被接住）

> 设计全文见 `意图路由与模糊兜底设计方案.md`；本节只讲「怎么用 / 怎么改 / 怎么验」。
> 代码：`intent.js`（判断）+ `app.js` 的路由段（接线）。历史单测 `intent.test.js` 已随清理移出磁盘（见 §一「历史单测」），当前回归以 `?debug=intent` 标签 + 真机走查为准。

### 1. 为什么要有这一层

旧链路只有一个语义维度（有没有金额）和两个出口（记账 / 整句否定）。结果是一句「明天约女朋友吃晚饭」
或「红糖糍粑」只能得到同一句否定提示 + 三个无关的金额示例，用户以为系统坏了。

现在一句话先落到 **7 个意图**之一，再按**缺哪个槽位只问哪个**承接，并且**同一句提示绝不连续出现**。

| intent | 中文 | 例子 | 谁处理 |
|---|---|---|---|
| `record` | 记账 | `午饭食堂 15` | `startFlow`（原有流水线，零改动） |
| `record` 缺金额 | 记账·缺金额 | `奶茶` / `一双鞋` | `fuzzyAskAmount`（L2 金额按钮） |
| `record` + `plan` | 未来计划 | `明天约女朋友吃晚饭` | 先提醒「还没发生」，再问金额 |
| `query` | 查询 | `这个月奶茶花了多少` | `answerCategoryQuery` / `answerDetailQuery` / 余额卡 / 饼图 |
| `howto` | 问怎么做 | `忘记记昨天的怎么办` | `answerHowto`（方法 + 一键执行按钮） |
| `advice` | 求建议 | `怎么省钱` | 冷静法 / 省钱指南 / 赚钱指南（原逻辑） |
| `dataop` | 改删撤 | `记错了帮我删掉刚才那笔` | `handleDataOp`（撤最近一笔 / 列候选） |
| `chitchat` | 闲聊情绪 | `我今天好累啊` / `你好` | `answerChitchat`（承接 + 3 个出口） |
| `unknown` | 判不出 | `帮我看看` | 先 L4 示例，第三次起 L5 人工出口 |

明确命令（`查余额` / `设置预算` / `截图记账` …）仍然最优先，由 `commandMatch()` 在分类**之前**短路；
**「句子里带金额的一律当成记账」这条老规则保留原样**（`commandMatch` 的 `hasAmount` 门控 + 意图层的 V4 抬分，
两处同一判据），所以 `肯德基疯狂星期四 25`、`我想买个耳机 500` 依然走记账 / 冷静法。

### 2. 判定方式（可解释，不是黑箱）

- **18 个信号**：金额 / 模糊金额 / 消费动词 / 计划语气 / 过去时间 / 品类 / 怎么办 / 是否问句 / 疑问词 /
  问号 / 余额词 / 饼图词 / 统计词 / 指代 / 改删撤 / 情绪 / 求建议 / 空输入。金额判定直接复用 `NLP.findAmounts`，
  **没有第二套金额识别**。
- **权重矩阵**：18 信号 × 6 意图的整数分值，全部集中在 `INTENT.CONST.WEIGHTS`，可以逐格调，不用改逻辑。
- **4 条否决**：疑问式求助、查询句、改删撤都不许记成 `record`（V1-V3）；反过来，带金额且没有疑问结构的句子
  强制 `record ≥ 70`（V4，为不破坏老规则而存在）。
- **兜底**：分数不够但有品类词 → 按「记账缺金额」问一句（`奶茶多少钱？`）；2~8 字的短名词（`红糖糍粑`）
  也按缺金额处理并归「其他」。问候语短路在兜底之前，所以 `你好` 不会被问成「你好多少钱」。

阈值都在 `INTENT.CONST` 里：`SCORE_LOW=30`、`MARGIN_MIN=15`、`CONF_HIGH=0.75`、
`RECORD_DOMINANCE=0.70`、`FORCE_RECORD_MIN=70`。

### 3. 响应阶梯（同一件事最多问四次，且四次都不同）

| 层 | 触发 | 表现 |
|---|---|---|
| **L0** | 槽位齐 | 直接执行（记账回执 / 余额卡 / 饼图 / 方法卡） |
| **L2** | 首次缺金额 | 1 个问题 + 3 个金额按钮 + 「自己填」：`奶茶多少钱？点一下就行 👇 [8] [12] [18] [自己填]` |
| **L3** | 第二次 / 缺 ≥2 槽位 | 换形式：直接给表单 `[帮我填]`，或意图二选一 |
| **L4** | 第三次 | 换通道：`[午饭食堂 15] [昨天打车 15] [这个月奶茶花了多少]` |
| **L5** | 第四次 | 彻底放弃 + 3 个入口（**文案不含问号，不再要求重说**）：`[手动记一笔] [查余额] [怎么记账]` |

金额按钮的值都来自可解释来源：文本里的模糊量词（`十几` → `[15] [12] [18]`）、饮品价带、该品类近 30 天
P25/P50/P75、该餐段均值、冷启动参考价。**金额永不自动推断**（猜错等于污染数据）。

### 4. 反死循环与 pending

- `pendingCtx` 只放内存（**不写 localStorage**，刷新即清空），2 分钟 TTL；点历史卡片会因 id 不匹配被拒收。
- 追问层级由 `INTENT.resolveLevel()` 唯一计算，`promptKey = intent|missing|level`，同一 key 不许连着出现；
  `tries ≥ 2` 必须换 `formType`，`tries ≥ 3` 直接 L5。
- 换了一件**新东西**（上一条问「奶茶」、这条问「一双鞋」）会重开一轮 L2，不会顺着上一条的 `tries` 跳到 L5。
- 用户直接补一句金额（点按钮或打 `12`）就走 `applySlotValue` → `startFlow`，槽位作答不经过 `handleSend`。

### 5. 云端现在只做「第二意见」

`tier=high` 完全不请求云端（断网可演示、没有「思考中」等待）；`tier=low` 且确属意图歧义时，才用 **3 秒**
超时向云端要一个 `intent` 裁决，并且**只允许在本地 top2 内改判**：

1. 越界改判直接拒收；
2. 本地已判 `record` 且句子里有金额 → 禁止改判（V4 保护）；
3. 云端 `confidence < 0.6` 不采信。

想彻底关掉这条路，把 `app.js` 的 `CLOUD_VERDICT_ENABLED` 置 `false` 即可（断网态即此状态）。

### 6. 现场怎么自证

- 控制台 `AJ_INTENT_LOG()`：最近 200 条判定的 `intent / confidence / tier / missing / level / promptKey`。
- 地址栏加 `?debug=intent`：每条 AI 回复后追加一枚小标签，直接显示「这句话被判成了什么」。
- 回归：`?debug=intent` 标签 + 真机走查（历史单测 `intent.test.js` 已不在当前交付内，勿再执行）。
- 阈值调参的 4 个指标：`unknown` 率 < 12%、L5 触发率 < 3%、`record` 被纠正率 < 8%、
  **相邻两次「用户可见文案」相同 = 0**（`promptKey` 只是内部闸门，验收要看用户读到的那句话；
  唯一例外是 L5 终点卡，它本来就不再追问）。

### 7. 改这套东西时的红线

1. **任何「追问金额」的文案都必须来自 `INTENT.buildPrompt`**，不要在处理器里直接 `addAIMessage` 一句新问句——
   绕过 `resolveLevel` 就等于把死循环放回来。
2. **不要动** `commandMatch()` 里的 `hasAmount` 门控，也不要动 V4 的 70 分下限。
3. **`intent.js` 只能依赖 `data.js` / `nlp.js`**，保持 ES5（无 `let` / `const` / 箭头函数 / 模板字符串），
   改完先 `node --check intent.js`（历史单测已随清理移出磁盘，用 `?debug=intent` 现场核对判定）。

### 8. 与设计稿的偏离与补丁（评审备案）

以下每条都是「不这么做就有对应用例过不了」或「QA 复验发现的真实缺陷」，全部有单测守着：

| # | 偏离 / 补丁 | 为什么必须 | 守它的断言 |
|---|---|---|---|
| 1 | **SIG_EMOTION 收紧**：句子里已有品类证据时，不再认 `DATA.EMOTION_KEYWORDS`（奶茶/皮肤/打车…），只认 MOOD 词（累/烦/emo…） | 该词典是「情绪型**消费**」，`奶茶` 命中会让 chitchat 反超，直接丢单 | `奶茶 -> record`、`今天好累啊 -> chitchat` |
| 2 | **SIG_WH 剔除模糊量词**：判疑问词前先抹掉「十几/几十/几百/几块…」 | 「十几块的奶茶」里的「几」被当疑问词，账被抢成查询（P0 丢单） | `十几块的奶茶 => record`、`今天几号 => SIG_WH` |
| 3 | **新增 R4 指代兜底**：只给指代（`昨天那个` / `那笔`）且无金额、无改删动词 → `query/detail` | `NLP.classify('那笔')` 会命中「笔」→ 学习，R3a 会把询价抢成记账（P1） | `昨天那个 -> query/detail`、`那笔 -> query/detail` |
| 4 | **unknown 首轮 L4、第 4 次才 L5**：`unknownTries` 计数 | 设计 §3.5 第 11 行要求「想看啥？三个最常用入口」，一上来就 L5 太粗暴 | 无头冒烟 4 连击 |
| 5 | **R1b / R2 / V4 自带高置信**：这三条是硬规则，不参与分数竞争 | 否则 `我今天好累啊`(0.74)、`我想买个耳机 500`(84 vs 66)、`记错了怎么删掉` 的 tier 判不到 high | §4.5 第 15/18/20 行 |
| 6 | **L5 的 promptKey 追加尝试序号**（`record\|amount\|5#3`） | 第 4/5 次 key 否则必然相同，违反 §3.4「连续 5 次两两不等」；但**用户可见文案仍逐层不同**，只有 L5 终点卡会重复 | C1 / C5（可见文案两两不同） |
| 7 | **pending「换物品就重开」**：`sameItemText()` 字面判重 | 否则「奶茶」问完再问「一双鞋」会顺着上一条的 tries 直接跳 L5 | 冒烟：`奶茶 -> 一双鞋` |
| 8 | **弱查询证据降级**：只有「看看/查一下/统计/汇总」而无查询对象 → `unknown` | 否则 `帮我看看` 被判成 query，去查一个不存在的对象 | `帮我看看 -> unknown` |
| 9 | **金额按钮：饮品优先价带、品类取 P25/P50/P75** | 餐饮大类均值会把「奶茶」算成 72 元；设计 §3.5 要的是 8/12/18 | E2 / E3 |
| 10 | **topic 取值以 LEX 为准**：`记错了怎么删掉` → `topic=delete` | 设计 §4.5 第 15 行写 `edit`，但同表 §4.1.1 的 `HOWTO_TOPIC` 把「删」映射为 `delete`，两者冲突，取词表 | §4.5 第 15 条 |
| 11 | **SIG_CATEGORY 补规范类目名通道**：`detectSignals` 额外 `anyHit(t, DATA.CATEGORY_KEYS)`，`extractSlots` 优先把规范名写进 `slots.category` | `NLP.classify` 只认「奶茶/打车」这类口语词，认不出「餐饮/交通/购物」这些规范名本身，于是「上个月餐饮花了多少」退化成 detail（列出全部账单）而不是餐饮汇总 | `上个月餐饮花了多少 -> query/category/餐饮`、`上个月一共花了多少 -> query/detail`、`餐饮 -> record` |
| 12 | **C4 兼容薄壳 `localCommandName()` 无内部调用点** | 设计稿 C4 要求「改名 + 留薄壳」，故**刻意保留**并加 `【勿删】` 注释；它已在无头冒烟里被间接覆盖（点击 `data-cmd` → `handleSend` → `routeCommand` → `commandMatch`） | QA 脚本 Q7a/Q7c（壳必须在）、Q7b（保留为已知偏离） |

> 另：`commandMatch()` 的 `hasAmount` 门控与意图层 V4 是**同一判据的两处实现**（前者在分类前短路命令，
> 后者在打分里抬分），改任一处必须同步改另一处，否则「带金额一律记账」会从缝里漏掉。
>
> 另：§3.4「连续 5 次 promptKey 两两不等」这条度量，在「用户每次换一样东西」的场景下会天然不成立
> （物件名一换就是新场景，`tries` 归零，key 自然回到 `record|amount|2`）。真正要守的是
> **用户可见文案不得逐字重复**——单测 `C5 四层「用户可见文案」两两不同` 守的就是这一条，L5 终点卡是唯一例外。
